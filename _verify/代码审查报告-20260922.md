## 一、先说方法（它决定了这份报告能不能用）

1. **报问题前必须看控制流** —— grep 只能数出"调用了哪些函数"，数不出"在什么条件下才调用"。

**本次我自己的扫描器产生了 4 类假阳性，全部已核对并剔除**（详见文末"附录：被我排除的假阳性"）。

## 二、🔴 阻塞项（必须修）

### 🔴 P0 | 管理后台用的是**代码里写死的默认口令**，且已在线上生效

**位置**：`yibang-server/routes/admin.js:7-14`

```js
const ADMIN_TOKEN = process.env.ADMIN_TOKEN || 'yibang-admin-2026';  // ← 兜底值
function auth(req, res, next) {
  const token = req.headers['x-admin-token'] || req.query.token;      // ← 还允许走 query
  if (token !== ADMIN_TOKEN) return res.status(401).json({ code: 401, msg: '未授权' });
  next();
}
```

**为什么是阻塞项（已实测，不是推测）**：

```
线上 .env 里没有 ADMIN_TOKEN          → 走的是代码里的默认值
curl -H 'x-admin-token: yibang-admin-2026' /api/admin/config  → HTTP 200  ✗ 真的进去了
curl -H 'x-admin-token: wrong-token-xyz' /api/admin/config    → HTTP 401  ✓ 校验本身是对的
nginx 无额外限制                      → 外网可直接访问
```

**影响面**（`/api/admin` 暴露的全部能力）：

| 接口 | 危害 |
|---|---|
| `GET /records` | **读取所有商户的全部账目** ← 核心资产泄露 |
| `GET /users` | 读取全部用户（openid / 手机号） |
| `POST /config` | **改写全局配置** —— 主题/文案/导航标题/功能开关，等于可篡改整个应用外观 |
| `GET /stats` | 平台经营数据 |

**建议**（三步，30 分钟内可完成）：

1. 在 `.env` 里设一个高强度随机值：`ADMIN_TOKEN=<openssl rand -hex 32>`
2. **删掉兜底值，改成启动即失败**：
   ```js
   const ADMIN_TOKEN = process.env.ADMIN_TOKEN;
   if (!ADMIN_TOKEN) throw new Error('必须配置 ADMIN_TOKEN —— 不允许用默认口令启动');
   ```
   > 这条比第 1 条更重要：**漏设环境变量必须"启动就炸"，而不是"悄悄用一个公开口令继续跑"**。
3. 去掉 `|| req.query.token` —— URL 里的 token 会进 access log、Referer、浏览器历史。

### 🟡 P1 | 写账**不在事务里**（余额可能短暂不一致）

**位置**：`yibang-server/routes/record.js`（create / update / delete 三处）
全库 `beginTransaction` / `commit` / `rollback` 出现 **0 次**。

**实际风险有多大（我核过，不是吓人）**：写序是「先 INSERT 明细 → 再 `recalcBalance()` 重算往来余额」。
如果第二步失败（网络抖动、进程重启），**明细已入库、余额还是旧值** ✗

**但影响是有界的**：`recalcBalance`（`lib/ledger.js:129`）是**全量重算**（对该对象的全部明细 SUM），
不是增量加减 —— 所以**该对象下一次任何写入都会把它修正回来** ✓

**结论**：不是数据永久损坏，而是"某笔往来在下次写入前显示错的余额"。

**建议**：
1. 把「INSERT + recalcBalance」包进事务（`pool.getConnection()` → `beginTransaction` → `commit/rollback`）；
2. 或者接受现状，但**加一个对账脚本**（每天跑一次，重算全部 `contacts.balance`），既能自愈也能发现异常。

### 🟡 P2 | `.sheet` 的底部覆盖散在 7 个文件，**曾 6 个页面同时漏掉**

**现状**：同一个类名在 ≥3 个文件里各定义一次的，共 8 个：
`.sheet`(7) `.page-head`(4) `.f-block`(3) `.f-label`(3) `.section-title`(3) `.bottom-space`(3) `.page-head-left`(3) `.page-head-right`(3)

`.sheet` 那 7 处里，6 处是**二级页覆盖 `bottom`**（避让键盘）。这件事必须每页各写一次，
而**历史上 6 个页面同时漏了** —— 结果就是弹层里有输入框的页面被键盘压住、点不到。

**建议**：把"弹层底部位置"变成一个变量（`--sheet-bottom`）在公共层算好，
二级页只需设 `--sheet-bottom`，不必各自重写整条 `bottom` 规则。漏一次的成本从"功能坏掉"降到"位置偏"。

**说明**：我逐条看过后端 8 处、前端 15 处空 catch，**绝大多数是刻意的**

`routes/file.js:114`
```js
try { row.file_url = await oss.getSignedUrl(row.file_url, 7 * 24 * 3600); }
```

## 附录：前 3 条的修复说明（2026-09-22 当晚）

### 第 1 条 · 管理后台口令

```js
// 改前
const ADMIN_TOKEN = process.env.ADMIN_TOKEN || 'yibang-admin-2026';
const token = req.headers['x-admin-token'] || req.query.token;

// 改后
const ADMIN_TOKEN = process.env.ADMIN_TOKEN;
if (!ADMIN_TOKEN || String(ADMIN_TOKEN).length < 16) {
  throw new Error('必须配置 ADMIN_TOKEN（≥16 位随机串）—— 不允许用默认口令或弱口令启动');
}
function auth(req, res, next) {
  const token = req.headers['x-admin-token'];   // 只认 header
  ...
}
```

**三处改动的用意**（第 2 条最容易被忽略）：
1. 设一个 64 位随机口令（`openssl rand -hex 32`）；
2. **删掉兜底值、改成启动即抛错** —— 漏设环境变量必须"启动就炸"，
   而不是"悄悄用一个公开口令继续跑"。**这一条比第 1 条更重要**：
   默认值的问题不在于它弱，而在于**它让配置缺失变成了静默**。
3. 去掉 `req.query.token` —— URL 里的凭证会进 nginx access log、Referer、浏览器历史。

**验证**（口令全程程序化从 `.env` 读取，只打尾 4 位核对，不转录原文）：

| 场景 | 期望 | 实测 |
|---|---|---|
| 服务能否正常启动 | 能 | ✅ |
| 旧默认口令（header） | 401 | ✅ 401 |
| 旧默认口令（走 query） | 401 | ✅ 401 |

### 第 2 条 · `admin.js` 的错列名

修的时候**刻意用别名保住 `title` / `contact` 这两个字段名**：

```sql
SELECT r.id, r.user_id, r.type, r.amount, r.category,
       r.content AS title,          -- 原 r.title（不存在）→ 用 content 顶上
       c.name    AS contact,        -- 原 r.contact（不存在）→ 关联往来对象表
       DATE_FORMAT(r.record_date, '%Y-%m-%d') AS record_date,
       r.created_at, u.nickname
FROM transactions r
LEFT JOIN users u    ON r.user_id = u.id
LEFT JOIN contacts c ON r.contact_id = c.id
ORDER BY r.id DESC LIMIT ? OFFSET ?
```

**为什么必须用别名**：后台页面 `admin/index.html` 渲染的就是 `r.title` / `r.contact`，
直接换成新字段名会让表格全部显示 `-` —— **那是一个 bug 换另一个 bug**。
顺带把 `record_date` 用 `DATE_FORMAT` 取成字符串，避免重蹈本项目"DATE 被当成 Date 对象、
序列化后少一天"的覆辙。

### 第 3 条 · `/record/ai-parse` 限流 —— **修的过程中发现原报告低估了问题**

原报告写的是"缺限流"。实际去看代码，**它连计数都没有**：

```js
// 全文件 grep bumpCount → 0 处
router.post('/ai-parse', auth, async (req, res) => {   // 既没 aiLimit，也没 bumpCount
```

而 `aiLimit` 的实现是 `const used = counters.get(key) || 0; if (used >= quota) ...` ——
**计数只由 `bumpCount(req)` 累加**。所以：

> **只挂 `aiLimit('parse')` 而不加 `bumpCount` = 一个"看起来修好了"的假修复 ——
> 限额永远停留在 `0/80`，永不触发。**

必须两处一起改：

```js
const { aiLimit, bumpCount } = require('../lib/rate-limit');   // ① 引入
router.post('/ai-parse', auth, aiLimit('parse'), async ...      // ② 挂中间件
const raw = await callModel({ ... }, 45000);
bumpCount(req);                                                 // ③ 调用成功后计数
```

`QUOTAS` 增加 `parse: 80`（正常老板一天记 20~30 笔，离 80 还远；恶意账号最多刷 80 次，预算烧不穿）。

**验证（决定性）**：临时把配额改成 1 → 连续调两次：

```
第 1 次调用 → code=0
第 2 次调用 → code=429  {"used":1,"quota":1,"type":"parse"}   ✅
```

**这个测法的价值**：它一次证明了"计数生效"和"限额触发"两件事。
如果只测"能不能调用成功"，假修复也能通过 —— 那是最危险的情况。
