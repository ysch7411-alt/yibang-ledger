OCR 选型验证报告

2026-09-19 · 易帮账本 · 8 个模型 × 5 档难度 × 2 个任务，全部线上实测

结论

用 qwen3-vl-flash（通用视觉模型），不要用"专用 OCR 模型"。

而且——我上一轮判断错了。当时我拿一张干净图跑了 3 轮全对，就选了 qwen-vl-ocr-latest； 这次补上难度梯度后，它的真实通过率只有 2/5，而通用视觉模型是 8/10。已经换掉。

一、为什么要"专用 OCR 模型"反而不行

因为它做的是逐字认字，不是把表格理解成结构 —— 这是两种能力。让它一边认字一边输出 JSON 时， 小字会被读错。最直接的证据在「拍远」那档（把单据缩到 800px，模拟站得远一点拍）：

四、顺手修掉两个真问题

  • 我上一轮关于压缩的说法是错的，已更正。 「只降画质」其实只省 24%（实测 544KB → 质量85:504KB / 质量75:412KB / 质量60:312KB）， 不是我说的"省一半以上"。真机上传 555KB 约 2.4 秒，这么压大概省 0.5 秒。 缩尺寸才是大头，但单据上的小字金额靠分辨率认，且 compressedWidth 需要基础库 2.26+（项目是 2.19.4）， 在开发者工具里验证不了 —— 所以暂不做，等能验证时再上。
  • 模型会把提示词里的示例当正文照抄。 你那几张照片里有一张没有明细的证明，模型给它编出了一行 螺纹钢 / 空规格 / 吨 / 0 × 0 = 0 —— 根因是提示词里写了「品名（必填，如「螺纹钢」）」，它照抄了例子。 已做两道修法：提示词去掉具体业务名示例并加一句"没有明细就返回空数组"；出口再过滤掉数量/单价/金额全为 0 的行。 修完那张图：1 行垃圾 → 0 行，耗时 1816ms → 1139ms。

这次最该记住的不是选了哪个模型

是验证方法错了会得出错的结论。一张干净图跑 3 轮全对，看起来证据很足，其实样本太窄 —— 换个难度立刻翻车。以后选模型必须：真值已知的图 + 难度梯度 + 每格至少 2 轮 + 认字和理解结构分开打分。 这套方法已经写进项目笔记，下次不用从头摸。
