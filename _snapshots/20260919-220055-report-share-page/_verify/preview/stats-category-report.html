一、一句话说清做了什么

合并成一张，是「表头合并」，不是把明细行揉在一起。
一张采购单 = 一笔账（一条支出流水）。但明细行的每一行上单独记住 supplier_name（这行是谁家的）、category（这行算哪一类）、 source_file_id（这行来自哪张照片）。 统计走明细行，所以一张单子里有几家的货，钱就分到几家头上。

流程

拍 3 张单子→ 逐张识别→ 合并成 1 张待核对→ 核对页按来源分组→ 确认入库（1 笔账 + N 行明细）→ 按供应商 / 按品类看

二、界面

按供应商 · 合计 + 排行 + 占比条
按品类 · 同一批数据换个维度
核对页 · 3 张合并成一张，按来源分组
核对页 · 品类可点改（当前项高亮）

三、几个刻意的设计选择

做法为什么
统计走明细行，不走表头 表头只有一个供应商名。多供应商的单子一旦合并，按表头统计就把几家的钱糊成一团 —— 那样「合并」就白合并了。
合并时逐行补 supplierName 这是「按供应商统计」能成立的前提。漏了这一步，多张合并的单子统计会全落进「未写供应商」。
占比条以榜首为 100%，最小 6% 以总额为基准的话，一家独大时其它全是一条看不见的线；最小 6% 保证尾巴上的小项也看得见，用户不会以为漏了。
区间口径集中在 fmt.rangeOf() 区间是「口径」不是「样式」。各页各写一套日期加减，迟早在报表上出现「采购页说本月、别的页说上月」。
取不到数据返回 null 绝不返回一份全 0 的假报表 —— 否则页面会把「服务挂了」显示成「本月没花钱」。
「未分类」是一个合法选择 宁可空着，也别为了好看硬归一类。视觉上用虚线描边，比真品类轻。
品类可点改（底部弹层） AI 归类不一定准。没有这个纠正口，归错一次就永远错下去，统计跟着错到底。
.seg 不用实心橙 分了两套语义：.chip（实心橙）= 筛掉一部分数据；.seg（浅底橙字）= 换角度看同一批数据。seg 不改变数据范围，不该抢主按钮的位置。

五、途中的一次事故（已修复，值得记录）

⚠️ cat file >> x 在这台机器上不是追加，是从第 1 字节覆写
我给 purchase.wxss 追加样式块，文件总行数几乎没变，看起来成功了。 实际开头 62 行被吃掉，覆写边界还把第 63 行啃掉 3 个字节 （  font-weight: 700; → ont-weight: 700;）。 丢的是文件头注释、.line1、.po-head、.po-head-top、 .po-supplier、.po-total、.po-meta、.po-row 以及 .po-no 的属性头。

怎么发现的：改完立刻 wc -l + grep -n 对行号，发现 .po-group-no 从 369 行跑到了 366 行。只 tail 看一眼会被旧输出骗过去 —— 第一版我就是这么被骗的。

怎么修的：写了一个先校验伤口形状、不对就一个字节都不写的脚本： 确认总行数 / 撕裂行 / 相邻行三者全对才动手；按设计稿（px×2 = rpx）重建丢失规则； 收尾五道自检（括号配平、关键类齐全、追加块唯一且在末尾、撕裂行已补全、改名命中数符合预期）。 先 --dry 演练，再落盘，结果与设计稿逐字一致。
根因不是手滑，是没有版本控制。同类事故同一天发生了三次，每次只能靠人肉对照设计稿重建。 已补上 _verify/snapshot.sh 源码快照（只收源码，排除 node_modules / .git / uploads）：
基线 20260919-203255-stats-category · 改后 20260919-203834-after-stats-category （各 222 文件 / 3.2M，--verify 通过）。动手改一批文件前打一个，改完再打一个。
