三、审计中发现并已修复的 4 个问题

已修复 1. 请求体解析失败误报 500（严重）

现象：给任意接口发一个不合法 JSON 体，返回 HTTP 500「服务器内部错误」；因为 express.json() 在路由之前执行，连「接口不存在」的 404 兜底都被它吃掉，所有请求齐刷刷 500。

危害：客户端发坏了，报成服务端故障。真出问题时排查方向完全错，而且分不清「偶发请求异常」和「服务真挂了」。
根因：express.json() 解析失败会 next(err)，一路落到最后的全局错误处理变成 500。
修法：在 body 解析中间件之后紧跟一个 4 参错误处理器，返回 400 请求体不是合法 JSON。
怎么发现的：审计脚本给 GET 传了 data:null，axios 序列化成字符串 "null" —— 脚本的坑反而炸出了真 bug。

已修复 2. /staff/approve 假成功

不传任何参数时，UPDATE ... WHERE id=NULL 影响 0 行，接口照样回「审核完成」。违反项目自己定的「不假装成功」原则。
已加参数校验（缺 id → 400、status 非 1/2 → 400），并用 affectedRows 判断真的改到了没有，改不到就回 404 没有找到这笔待审记录。

已修复 3. /share/create 空参数也建记录

空参数会建出一条 type=NULL 的分享记录，打开后谁也不知道该显示什么。已校验 type（1 每日汇总 / 2 客户对账）、type=2 时必须给 contact_id、expire_days 限 1~365。

已修复 4. 审计脚本自身的坑

GET 请求带 data: null 被 axios 序列化成字符串，攻击了自己的服务端；另外判定逻辑把「故意测 404 兜底」的用例也当失败。都已修正 —— 审计工具本身也得先可信。
