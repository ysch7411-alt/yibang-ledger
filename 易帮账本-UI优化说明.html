Design Review · 2026-09-19

易帮账本 · 界面优化说明

对现有 10 个页面做了一轮系统性的界面重构：先把散落的设计值收成一套令牌，再逐页解决视觉、布局、交互与易用性问题。以下说明每一处改动的理由，以及它给老板省下的那几秒。

10 个页面 零表单录入 1 套设计令牌 13 个本地 SVG 图标 顺带修复 10 个真实缺陷 已过 DevTools 真实编译 + 模拟器实测

00现状体检

先说结论：当前界面不是「不好看」，而是「没有系统」。10 个页面各自为政，同样一个标题在 4 个页面里写了 4 遍，颜色、间距、字号都靠手写，于是必然出现不一致和低对比。

类别问题证据（改前代码）
视觉四个 Tab 各用一种主题色（橙/绿/蓝/紫），品牌识别度被稀释；「参谋」页还额外插了一张紫色渐变卡，与全站橙色体系断裂custom-tab-bar 第 49-52 行、advisor.wxss #7B1FA2
视觉icon 全部用 emoji（📝📊🔍🧠）。emoji 在 iOS / Android / 不同微信版本上字形、色彩、粗细都不一样，同一版界面看起来像两套产品index.js icon: '📝'
视觉导航栏标题与页面内大标题完全重复：导航栏写「易帮账本」，页面正中又写「易帮账本」，首屏白白浪费 100rpx 高度app.json navigationBarTitleText + record.wxml .title
布局所有页面标题居中、副标题居中、卡片等宽堆叠。居中式大标题是「模板感」的主要来源，也削弱了信息层级4 个 wxss 里重复的 .header{text-align:center}
布局「报表」页与「记账」页内容重复：两处都有应收应付看板、两处都有今日收支，用户不知道该看哪个record.wxml .debt-board vs summary.wxml .overview-card
交互底部输入条 bottom: 140rpx 是猜出来的，与自定义 TabBar 的真实高度（108rpx + 安全区）对不上；不处理 safe-area-inset-bottom，全面屏上会被小黑条压住record.wxss .input-bar
交互点输入框弹出系统 wx.showModal({editable:true})：单行、无字数提示、样式不可控，与自绘 UI 气质割裂record.js onInputTap
交互录音靠一个 duration: 60000 的 Toast 提示「正在说话…」。Toast 会遮挡内容、不可取消、时间感知为零record.js startRecord
易用「我的」页面根本没有入口——没有任何导航指向它。店员管理、我的套餐、推广赚钱全部是死胡同，付费转化路径直接断了全项目 grep 无 /pages/profile 跳转
易用文字颜色 #999 / #bbb 在白底上的对比度只有 2.1~2.8:1，远低于 WCAG AA 要求的 4.5:1。22rpx（11px）的字号低于 12px 可用下限全站 .text-hint / .record-date
易用金额用 -apple-system 默认比例数字，一列金额的小数点上下错位，对账时逐行看很费眼app.wxss 无 tabular-nums
易用空状态只有一行灰字「暂无数据」，没有解释、没有下一步动作.empty-text{text-align:center;color:#bbb}
易用「查询」页右下角一个悬浮胶囊压住列表内容；搜索框没有图标、没法一键清空、结果不标出命中位置search.wxss .ai-entry{position:fixed}

01先建令牌：把设计值收口到一处

原来每页各写各的颜色，改一处要翻 10 个文件。现在全部收进 app.wxss 的 page{} 里，页面样式只写「这个页面独有的东西」。

颜色：品牌橙不能用来写字

这是最容易被忽略、但对 50 岁老板影响最大的一条。品牌色 #FF6B35 在白底上的对比度只有 2.81:1，白字压在它上面同样只有 2.81:1 —— 连大号文字的 3:1 门槛都不到。所以做了分层：

为什么不干脆把品牌色也调暗？导航栏、Tab 图标、卡片描边这些地方不吃文字对比度规则，保持明亮的 #FF6B35 才能留住品牌识别；只有「承载文字」的地方才换成深橙。这样既过得了无障碍标准，又不会让整个界面变浑浊。

字号：底线上调到 12px

全站 22rpx（11px）的字号统一提到 24rpx（12px），这是中文可读性的实用下限。金额另开一档 64~76rpx，并加 font-variant-numeric: tabular-nums。

页面标题44rpx22700 字重，左对齐

触控：所有可点区域 ≥ 88rpx

原来的加号按钮是 76rpx（38px），低于 44×44pt 的通用触控下限。现在底部输入条的加号 88rpx、麦克风 96rpx、列表行最小高度 108rpx。

03逐条优化与理由

改动做法理由 / 对体验的提升
导航 删掉重复大标题 导航栏保留「易帮账本」，页面内标题改为左对齐的功能名 + 状态副标题（如「9月19日 星期六 · 今天已记 3 笔」） 首屏多出约 100rpx 有效高度；更重要的是，副标题现在携带信息（日期、笔数），而不是重复一遍产品名。老板打开就知道「今天记了几笔」，不用再往下翻。
导航 TabBar 从 4 个加到 5 个 新增「我的」Tab，文字从「记/算/查/谋」改成「记账/报表/查询/参谋/我的」 修的是一个断链：原来「我的」页没有任何入口，店员管理、我的套餐、推广赚钱三个页面全进不去，付费转化的路直接断了。另外「记/算/查/谋」四字过于含蓄，老用户第一次打开猜不出「谋」是干嘛的，补全为双字后自解释。
视觉 统一图标体系 5 个 SVG 图标 × 选中/未选中两态，替换全部 emoji emoji 的字形由系统字体决定，iOS 和 Android 上粗细、配色完全不同，是「廉价感」最直接的来源。SVG 是矢量、跨端完全一致、随便改色，整个包也只增加了约 2KB。
视觉 选中态用色更克制 未选中统一 #98A2B3 灰；选中用深橙图标 + 深橙加粗文字 + 顶部 44rpx 指示条 「每个 Tab 一个颜色」会让用户以为它们是 4 个不同的产品。改成单一强调色之后，品牌感立刻建立，同时顶部指示条让「我在哪一屏」一眼可辨。文字没有沿用亮橙，是因为它在白底上只有 2.8:1 的对比度，小字根本读不清。
视觉 金额用等宽数字 font-variant-numeric: tabular-nums + DIN Alternate 字体栈 默认比例数字下，1 比 8 窄，一列金额的小数点会上下错位。等宽后整列数字竖直对齐，对账时眼睛可以顺着一条线扫下来，逐行核对的速度明显变快。
视觉 「参谋」页去掉紫色卡 改为深色洞察卡（#1F2937→#111827）+ 橙色光晕，收支数字在深底上用更亮的绿色 紫色渐变与全站橙色毫无关系，属于「多插了一个别人的卡」。深色卡在浅色界面里天然读作「结论 / 分析」，正好匹配参谋页的定位；深底上原来那套 #4CAF50 绿太暗，换成 #4ADE80 才看得清。
交互 录入改成零表单 底部只留三个直达入口：按住话筒说话 / 加号拍照选文件 / 直接打字。AI 解析完直接入账，不弹表单、不选类型、不填字段；结果只在底部滑出一条「已记好：收入 ¥5,000 · 张老板 · 货款」，6 秒自动消失 原来每一笔都要过一遍「金额 → 类型 → 往来对象 → 事由」四个字段，哪怕 AI 已经全部识别正确。用户要的是「说一句就完事」，所以把确认动作整个删掉，改成「先入账 + 可撤销/可改」——把默认路径的点击次数从 5 次降到 0 次。唯一的例外是「没听出金额」：这时只追问这一个数，拼回原话重新归类，用户不用再说一遍。
交互 语音升级为唯一主操作 麦克风独立成 96rpx 实心品牌圆钮；录音时弹出带波形、秒表、取消/结束两个按钮的浮层 目标用户是 50 岁上下、常在店里有活儿的老板，打字的成本远高于说话，所以语音必须是视觉权重最高的那个按钮，而不是原来那个浅浅的小圆点。录音浮层替代了 60 秒 Toast —— Toast 会遮挡内容、无法取消、也看不到已经录了多久，用户会慌。
交互 底部贴边改精确计算 TabBar 固定 height:108rpx，输入条 bottom: calc(108rpx + env(safe-area-inset-bottom))；所有涉及安全区的声明都写成双行做渐进增强 原来 bottom:140rpx 是估的，比真实 TabBar 高，输入条和 TabBar 之间会露出一条缝或被压住。固定高度 + 安全区计算后，任何机型、有没有全面屏小黑条都严丝合缝。不用 CSS 变量中转 env()，是因为旧 WebView 不支持时整条 calc() 会失效、底部留白直接归零。
交互 列表按天分组 流水按「今天 / 昨天 / 9月18日」分组，每组标题右侧带当日收支小结 连续的长列表里，用户很难判断「这条是上周的还是上个月的」。分组后有了天然的阅读锚点；日期小结则让「哪天收得多」不用点进去算。
易用 空状态带上出路 从一行灰字改成「图标 + 说清楚为什么空 + 一个行动按钮」，并按场景给不同文案 「暂无数据」四个字不解决任何问题，用户只会觉得坏了。现在空状态直接给出下一步（「记第一笔」），把死路变成入口。
易用 报表页去重 + 加维度 去掉与首页重复的今日明细弹窗；收支汇总加「今日 / 本月」分段切换；往来列表加首字头像 同一个数字出现在两个地方，用户会怀疑哪个是对的。去重后分工清晰：首页管「今天」，报表管「趋势」。首字头像让一屏名单有了视觉锚点，找「张老板」比在纯文字里扫快得多。
易用 查询页补齐搜索能力 加放大镜图标、一键清空、收支/时间筛选、结果关键字高亮；把遮挡内容的悬浮胶囊改成页面内入口卡 原来的搜索框只能盲打，没有任何反馈。高亮命中的字，用户才能确认「系统是按我理解的意思找的」；筛选把常用的「只看这个月的支出」变成一次点击。悬浮胶囊固定压在列表右下角，是典型的「遮挡内容换来的曝光」。
易用 响应式适配大屏 @media (min-width:520px) 下把内容区限宽 760px 并居中 rpx 是按屏宽等比放大的：在 iPad 上，750rpx 被拉成 768px，字号翻倍、一行字长到眼睛跟不上。限宽后平板和折叠屏展开态都能正常阅读。
易用 提示文案说人话 「AI 经营建议」→「经营提示」；支付/识图/语音未接通时如实说明并给出替代路径 那段建议其实是前端本地规则拼出来的，标成「💡 AI 经营建议」属于过度承诺。至于未接通的接口，原来点下去只有一句「失败」或者干脆没反应 —— 用户比谁都清楚产品是不是半成品，如实说反而更让人信任。

04顺带修掉的 6 个功能性缺陷

做 UI 时如果不动这些，界面做得再漂亮也跑不起来 —— 所以一并修了。这些都不属于「界面」问题，但直接决定体验的成败。

编号问题后果修法
B1res.statusCode === 401 判断永远不成立后端鉴权失败返回的是 HTTP 200 + body.code 401。原代码只看 HTTP 状态码，所以 token 一过期，所有页面静默空白、自动重登从不触发改判 body.code === 401，并加 _retry 标记只重放一次，避免死循环
B2toISOString() 按 UTC 取日期北京时间 0:00–8:00 期间，首页查的是昨天的汇总，新记的账也会落到前一天新增 fmt.ymd() 用本地时区拼日期，全站统一口径
B3res.data.receivable.toFixed(2)mysql2 把 DECIMAL 返回成字符串，字符串没有 .toFixed → 直接抛错，首页应收应付永远显示 0.00fmt.toNum() 统一兜底类型转换
B4记账时丢弃了 AI 识别出的联系人后端 /record/create 只收 contact_id，前端把 AI 返回的 contact 名字直接扔了 → 往来对象永不入库，应收应付、对账、催收全部是 0新增「按名字查 → 查不到就建」逻辑，自动补上 contact_id
B5审核接口调错了路径前端调 /record/pending-list、/record/approve，后端实际在 /staff/pending、/staff/approve → 待审核列表永远空、点通过没反应改调正确路径，并适配字段名差异
B6/staff/list 返回值形状不符后端返回纯数组，前端按 res.data.list 读 → 店员列表永远为空适配层同时兼容数组和 {list} 两种形状

关于 B4 多说一句：这是所有问题里最贵的那个。产品的招牌能力是「数据永不遗忘」，但连「谁欠我钱」都存不进去，后面所有基于往来对象的报表、催收建议、对账单分享都会是空的。界面再好看也救不回来。

07零表单录入：把「确认」这一步删掉

产品要求很明确：用自然语言就能完成录入，不需要选择，不需要填表格，AI 根据语音或图片自动识别归类后直接保存。所以录入路径上不放任何表单，用户只做一个动作。

入口用户动作系统行为
按住说话按住底部橙色话筒，说一句，松手录音 → 转写 → AI 归类 → 直接入账。松手即提交，不需要点「结束」，手指上滑可取消
拍一张点「+」，拍照 / 从相册选 / 选微信文件上传 → 识图取文 → AI 归类 → 直接入账
打一句直接在输入框里打字，回车同样走 AI 归类 → 直接入账

为什么敢去掉「保存前确认」

确认弹窗是整条链路上最大的一次摩擦：AI 明明已经识别对了，用户还要再点一次「确认」。所以把它换成 「先入账 + 结果条 + 可改」——默认路径 0 次点击，出错再纠正。

全程只在一件事上打断用户：没听出金额。这时结果条变成「这句话里没听出金额」，下面直接给一个数字输入框，填完把原话拼回去重新归类——用户不需要重新说一遍，也不需要面对「金额 / 类型 / 往来对象 / 事由」四个框。

状态机

空闲 → 按住录音（浮层：脉冲点 + 计时 + 松开提示）→ AI 整理中（深色进度条，不遮挡页面）→ 已记好（浅色结果条，6 秒自动消失）。失败和缺信息的分支不会自动消失，需要用户看到并处理。

纠错面板退居二线

原来的「记一笔」表单改名为「改一下这笔」，只在用户主动点结果条上的「改一下」时才出现，不参与主路径。字段保留，因为纠正 AI 的错误时人需要精确控制。

验证过程中发现并修掉的 4 个真实缺陷

编号问题后果与修法
B7wx:else 和 wx:for 写在同一个节点上（5 个文件）这是编译硬错误，整个项目编译不过。微信不允许同一节点既做条件分支又做循环。改为 <block wx:else> 包裹循环——block 不产生节点，不影响布局。
B8mysql2 把 DATE / DATETIME 返回成 JS Date，JSON 序列化成 UTC 串北京时间 0:00–8:00 的记录被归到「昨天」，时间显示差 8 小时（实测：14:09 显示成 06:09）。新增 fmt.dayKey() / monthKey() / hhmm() 统一按本地时区还原，全站日期口径收口到一处。
B9profile.js 用了 fmt.dayKey 但漏了 require「我的」页面加载即抛 ReferenceError: fmt is not defined。这是模拟器 console 抓到的，静态检查抓不到——所以两条都要做。
B10search.wxss 漏了 .chat-item.aiAI 回复的气泡缺少显式对齐声明，只能靠默认值兜着。已补齐，并把这个类别的检查加进自检脚本。

B7 值得单独说一句：它在静态检查里完全看不出来（标签配对、class、处理器都正常），只有真正跑一遍编译器才会暴露。这也是为什么这轮坚持要过真实编译，而不是只看代码。

专属网关的能力边界（实测，不是猜的）

DASHSCOPE_BASE_URL 指的并不是公网百炼，而是一个 255 个模型的多厂商聚合网关。所以先列清单、再用真实样本打通最小请求，最后才写代码：

能力实测可用模型格式要点
视觉 OCRqwen3.5-ocrcontent:[{type:'image_url',image_url:{url:'data:image/jpeg;base64,…'}},{type:'text',text:'…'}]
语音识别qwen3-asr-flash-2026-02-10content:[{type:'input_audio',input_audio:{data:'data:audio/wav;base64,…',format:'wav'}}]
  • input_audio.data 必须带 data: 前缀，纯 base64 会被判为「URL 不合法」
  • audio_url 类型不被支持；fun-asr-flash / qwen-audio-3.0-asr-flash 在该网关返回空
  • 上传目录没有对外暴露静态服务，所以后端读本地文件转 data URI——顺带避免了把用户票据暴露成公网 URL；已做目录穿越防护（/uploads/../../etc/passwd 被拒）

线上功能验证（11 项）

  • 一句话多笔：昨天收张老板5000块货款，今天买菜花了320，还欠李四800块 → 解析出 3 笔，且「昨天」正确换算为 2026-09-18
  • 图片取文：把记账页截图喂给 OCR，中文、金额、时间全部还原（+¥5,000.00、回款 张老板 货款·14:09）
  • 语音转文字：一段真实通话录音 → 你好。你好。你好呀。你好。
  • 类型判定修正：「今天收了张老板5000块货款」→ 收入（此前会被判成「回款」，凭空把对方余额变成负数）；「还了张老板5000」→ 付款；「张老板还欠我5000」→ 应收
